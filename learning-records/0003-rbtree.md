# 第 2 课后用户反馈与第 3 课决策（LR-0003）

**Status:** active

用户第 2 课反馈明确且高质量,标志其理解力被进一步证实。

## Evidence（用户原话）

1. **pprev 已懂,且给出精准复述**:"pprev 指向指向我这个节点的指针的地址,这指向我节点的指针类型就是我这个节点的 next 的类型,不用转换。"
   → 抓到了类型统一这个深层点,这是大多数人漏掉的。用户用"类型 = next 的类型"推出 `**pprev` 的合理性,属于自顶向下的理解。
2. **额外的洞察**:"对于桶内第一个节点,指向我这个节点的指针的地址同时也是桶头的地址。"
   → 正确。深层原因:`first` 是 `hlist_head` 第一个成员,`offsetof==0`,所以 `&head->first == head`。用户从语义推出,未点到 offsetof,但结论对。
3. **实验预期一致** → 哈希表桶分布实验跑通,符合预期。
4. **第 3 课明确要求:"红黑树原理 + 真实"** → 要原理图,也要真实的 `struct rb_node` + 真实用例(我倾向 CFS 调度器)。

## Implications

1. **理解力档位上调**。用户能用类型推导而非死记,说明 C 语言功底足以支撑深入内核数据结构。第 3 课红黑树可以直接讲清 5 条性质 + 旋转 + 内核 rbtree API 的"半成品"设计哲学,不必过度简化。
2. **"原理 + 真实"是用户的明确要求**,不要只画树不碰代码,也不要只丢代码不讲性质。结构:性质→旋转直觉→内核 rb_node 真实定义→为什么内核 rbtree 不内置插入/搜索(设计哲学)→真实用例 CFS 的 vruntime。
3. **必须核验的边界**(影响课程准确性,不能靠记忆):
   - 6.6 里 CFS 是否仍用 rbtree?(EEVDF 在 6.6 合入,但 CFS 调度类的 rbtree 结构仍存)
   - 进程地址空间的 VMA 树已从 rbtree 迁到 maple tree(6.1 起),不能再说"VMA 用红黑树"——这是个常见的过时说法,用户环境是 6.6.87.2,必须讲对。
   - rbtree 的真实 API:`rb_node`/`rb_root`/`rb_insert_color`/`rb_first`/`rb_next` 等。
4. **实验设计**:用户能驾驭真实代码。实验用一个能编译的 `.ko`,维护一棵按"键值"排序的 rbtree,插入若干节点并中序遍历打印——纯软件,WSL2 可跑。
5. **风格**:继续引导 `u16` 风格;用户已接受。

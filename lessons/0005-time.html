时间子系统：jiffies、HZ 与两套定时器

你在 MCU 上用 SysTick 做心跳、用硬件定时器做精确定时—— 内核里这两件事对应的是 jiffies 和 hrtimer。这节课把这条迁移线打通。

本课的连接点

第 3 课你学的红黑树,这课会在 hrtimer 里见到它的真实用武之地—— 高精度定时器用 rbtree 按到期时间排序所有定时器。学过的东西立刻落地。

内核时间的两层抽象

内核管理时间不是一层,是两层,各有来历:

内核时间子系统 ┌─────────────────────────────────┐ ┌─────────────────────────────────┐ │ 低精度：基于 tick (jiffies) │ │ 高精度：基于硬件时钟 │ │ │ │ │ │ • 全局计数器 jiffies │ │ • ktime_t（纳秒级） │ │ • 每秒 HZ 次 tick 中断 │ │ • 独立于 jiffies │ │ • timer_list（时间轮） │ │ • hrtimer（红黑树） │ │ • 粒度：1/HZ 秒（毫秒级） │ │ • 粒度：纳秒/微秒级 │ └──────────────┬──────────────────┘ └──────────────┬──────────────────┘ │ │ └───────────────┬───────────────────────┘ │ 历史上先有低精度（tickless 之前）, 后来硬件能做高精度了,才加了 hrtimer 一层。 两套并存,各管各的场景。

为什么有两套?这是历史 + 工程的结果:早期硬件只能产生固定频率的 tick(比如 100 次/秒), 所有定时都是 tick 的整数倍,够用但粗糙。后来 CPU 有了高精度定时器(TSC、HPET),内核才加了 hrtimer。 但老接口 timer_list 仍保留——大量超时场景(网络重传、协议定时)根本不需要纳秒精度,用 jiffies 更省。

jiffies、HZ 与那个到处都是的转换

MCU / 裸机

SysTick 每 1ms 触发一次中断,中断里 tick_count++。需要计时时就读 tick_count,差值就是毫秒数。

"1 秒" = tick_count 增加 1000。

Linux 内核

每个 tick 中断里 jiffies 自增。"1 秒" = jiffies 增加 HZ。

HZ 是编译期常量(CONFIG_HZ),x86_64 默认 1000(服务器发行版常 250)。

// include/linux/jiffies.h
extern unsigned long volatile __jiffy_data jiffies;      // 32 位,会回绕
extern u64 jiffies_64;                               // 64 位,实际计数器
// jiffies 是 jiffies_64 的低 32 位别名;64 位系统上两者等价

// 64 位上读 jiffies 安全;但跨长间隔(>50天,32位)要用 jiffies_64

这就是为什么你在驱动代码里到处看到 msecs_to_jiffies() —— 内部计时统一用 jiffies, 所以"100 毫秒"必须先转成 jiffies 数才能比较:

// 驱动里要"等 100ms"或比较时间差,标准写法:
unsigned long timeout = jiffies + msecs_to_jiffies(100);
if (time_after(jiffies, timeout)) {
    // 超时了
}
// 注意:绝对不要写 jiffies + 100,要经过 msecs_to_jiffies
比较 jiffies 的坑:回绕

因为 jiffies 会回绕(32 位下约 50 天一圈),直接 jiffies > timeout 会出错。 内核提供 time_after(a, b) / time_before(a, b) 用减法处理回绕,永远用它们,别用裸比较。

两套定时器:timer_list vs hrtimer

这是本课的核心选型表。两套定时器的本质差别:

对比项timer_list（时间轮）hrtimer（高精度）
精度jiffies 粒度（1/HZ 秒，~1ms）纳秒级（ktime_t）
数据结构哈希时间轮（多级级联）红黑树（第 3 课学的！）
是否依赖 tick是否（独立于 HZ）
开销低，但有级联延迟尖峰稍高，但可预测
典型用途网络重传、协议超时、普通驱动超时多媒体、实时、需要 µs 精度
回调上下文软中断（不可睡眠）硬中断上下文（不可睡眠）

hrtimer 用红黑树——把所有定时器按到期时间排序,最左节点(最快到期)是 O(1) 取出。 这正是第 3 课 rbtree 的真实用武之地:O(log n) 插入、O(1) 取最值,完美契合"管理一堆按时间排序的定时器"。

两套都不能在回调里睡眠

无论 timer_list 还是 hrtimer,回调都跑在中断类上下文(软中断 / 硬中断), 都不能睡眠(对照第 4 课的上下文铁律)。需要睡眠的"延迟工作" → workqueue 或 threaded IRQ。

真实 API

低精度：timer_list（6.x 现代接口）

// 老接口 setup_timer / data 字段在 6.x 已移除。现代用 timer_setup:
struct timer_list {
    struct hlist_node entry;
    unsigned long       expires;          // 到期 jiffies
    void              (*function)(struct timer_list *);  // 注意签名:只收 timer*
    u32               flags;
};

// 注册:把回调绑到 timer 上
timer_setup(&dev->timer, my_callback, 0);

// 启动 / 重启(到期 jiffies)
mod_timer(&dev->timer, jiffies + msecs_to_jiffies(100));

// 取消(同步版,等回调跑完)
del_timer_sync(&dev->timer);

私有数据怎么办?老 API 靠 data 字段,6.x 改成"嵌入 + 反查":

struct my_dev {
    int               x;
    struct timer_list  timer;      // 嵌入
};

static void my_callback(struct timer_list *t)
{
    struct my_dev *dev = from_timer(dev, t, timer);  // 反查宿主(又是 container_of!)
    pr_info("tick, x=%d\n", dev->x);
}

看到 from_timer 了吗?它就是第 1 课的 container_of。你已经第三次撞见这个手法了—— 内核数据结构的统一美学。

from_timer 和 container_of 到底啥关系?为啥不直接用?

from_timer 就是 container_of 的薄包装宏,定义只有一行:

// include/linux/timer.h
#define from_timer(var, callback_timer, timer_field) \
    container_of(callback_timer, typeof(*var), timer_field)

包这一层有三个好处(本质都是防呆):

 直接用 container_of用 from_timer
参数(ptr, type, member) 全手填(var, ptr, field) 自动绑定
类型手写完整类型名typeof(*var) 自动推导
出错时顺序/类型填错编译器不报,运行时崩字段名和宿主类型绑定到变量名,难写错
改名时手写类型要改多处靠 typeof 推导,改一处即可

对比两种写法:

// 笨写法:三个参数全是手填字符串,容易错
struct my_dev *dev = container_of(t, struct my_dev, timer);

// from_timer:类型靠 typeof(*dev) 推导,字段名绑定
struct my_dev *dev = from_timer(dev, t, timer);

那为什么 hrtimer/list_head/rb_node 没有这种宏? 因为内核只为高频场景定制专用宏。timer_list 用得太广(4.15 去 data 字段时配套加了 from_timer + timer_setup), 值得专门做防呆包装;而 hrtimer、list_head、rb_node 直接用 container_of 原语—— 它们也有别名宏(list_entry / rb_entry),但本质都一样。直接用 container_of 完全没问题,只是少了防呆保护。

高精度：hrtimer

struct hrtimer {
    struct timerqueue_node  node;     // 内部建在 rbtree 之上
    ktime_t                 _softexpires;
    enum hrtimer_restart    (*function)(struct hrtimer *);
    struct hrtimer_clock_base *base;
    /* ... */
};

// 初始化:选时钟(CLOCK_MONOTONIC)和模式(相对/绝对)
hrtimer_init(&timer, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
timer.function = my_hrtimer_cb;

// 启动:1ms 后到期(ktime_set(秒, 纳秒))
hrtimer_start(&timer, ktime_set(0, 1000000), HRTIMER_MODE_REL);

// 回调:返回 RESTART 就 forward 后继续,NORESTART 就停
static enum hrtimer_restart my_hrtimer_cb(struct hrtimer *t)
{
    /* 做事 */
    hrtimer_forward_now(t, ktime_set(0, 1000000));   // 往前推 1ms
    return HRTIMER_RESTART;
}

私有数据怎么办?和上面的 timer_list 一样——hrtimer 本身不带业务数据, 它也是个侵入式挂钩。你的数据结构把 hrtimer 当字段嵌进来,回调里用 container_of 反查宿主:

struct my_dev {
    int           x;
    struct hrtimer  timer;      // 嵌入(和 timer_list 一模一样)
};

static enum hrtimer_restart my_hrtimer_cb(struct hrtimer *t)
{
    struct my_dev *dev = container_of(t, struct my_dev, timer);  // 反查宿主
    pr_info("tick, x=%d\n", dev->x);
    hrtimer_forward_now(t, ktime_set(0, 1000000));
    return HRTIMER_RESTART;
}

注意这里没用专门的宏(像 timer_list 的 from_timer),而是直接用 container_of—— 这反而更直白地暴露了本质:hrtimer 就是第 1 课 list_head 那套"数据嵌入挂钩"手法的又一次复用。

挂钩家族大集合:你已经全会了

把这几课学的串起来,内核里所有"挂钩 + 反查宿主"的结构全是同一招:

挂钩建在反查宏第几课见过
list_head—list_entry / container_of第 1 课
hlist_node—container_of第 2 课
rb_node—rb_entry第 3 课
timer_list时间轮from_timer第 5 课
hrtimerrbtreecontainer_of第 5 课(这里)

数据嵌入挂钩,回调/遍历时 container_of 取回宿主—— 记住这一句,内核里 work_struct、sk_buff、page 等成百上千个结构你都能一眼看穿。

动手实验:hrtimer 周期任务(WSL2 可跑)

目标:用 hrtimer 做 1ms 周期任务,跑 50 次后自停。对比第 4 课的 workqueue 方案—— 你会发现 hrtimer 精度高得多(workqueue 受 HZ 限制,hrtimer 不受)。 

// bt_hrtimer.c — 第 5 课实验:hrtimer 高精度周期任务
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/hrtimer.h>
#include <linux/ktime.h>

static struct hrtimer bt_hr;
static unsigned int  bt_count;
static ktime_t        bt_period;

static enum hrtimer_restart bt_hr_cb(struct hrtimer *t)
{
    bt_count++;
    if (bt_count <= 5)     // 只打印前 5 次,避免刷屏
        pr_info("bt_hr: tick %u\n", bt_count);

    if (bt_count >= 50) {
        pr_info("bt_hr: 完成 50 次,停止\n");
        return HRTIMER_NORESTART;
    }
    hrtimer_forward_now(t, bt_period);
    return HRTIMER_RESTART;
}

static int __init bt_hr_init(void)
{
    bt_period = ktime_set(0, 1000000);    // 1ms = 1,000,000 ns
    bt_count = 0;

    hrtimer_init(&bt_hr, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
    bt_hr.function = bt_hr_cb;
    hrtimer_start(&bt_hr, bt_period, HRTIMER_MODE_REL);

    pr_info("bt_hr: 启动 1ms 周期 hrtimer\n");
    return 0;
}

static void __exit bt_hr_exit(void)
{
    hrtimer_cancel(&bt_hr);     // 同第 4 课:卸载前必须取消
    pr_info("bt_hr: 卸载,共 tick %u 次\n", bt_count);
}

module_init(bt_hr_init);
module_exit(bt_hr_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 5: hrtimer periodic demo");
  1. make → bt_hrtimer.ko
  2. sudo insmod bt_hrtimer.ko
  3. dmesg | tail —— 应看到前 5 个 tick,然后 50 次时"停止"。整个 50ms 内完成
  4. 对比第 4 课 workqueue 的 1 秒间隔:这里 1ms,精度高三个数量级
  5. sudo rmmod bt_hrtimer —— 看"共 tick X 次",应≈50
观察重点

50 次 tick 在约 50ms 内完成——如果用第 4 课的 workqueue 做不到这个精度(它受 HZ 限制,最小约 1ms 还有调度抖动)。 hrtimer 直接靠硬件时钟驱动,这就是"高精度"的可观察证据。

注意 hrtimer_cancel 与第 4 课 cancel_delayed_work_sync 是同一种模式: 卸载前必须取消未决的异步工作。这个"取消模式"你会在每个驱动里反复写。

delay 家族:何时忙等,何时睡眠

这是你写驱动时每天都要做的选择。"等一会儿"在内核里有两种实现,选错会浪费 CPU 或踩上下文坑:

函数类型可用上下文何时用
udelay(n)忙等(CPU 空转)原子/中断 OK很短(<10µs),需精确
mdelay(n)忙等(包装 udelay)原子/中断 OK不推荐,能改 msleep 就改
usleep_range(min, max)睡眠(让出 CPU)仅进程上下文10µs–20ms 首选
msleep(n)睡眠(让出 CPU)仅进程上下文>20ms;短延时易超调
经典选型口诀

在中断/原子上下文:只能 udelay(忙等,因为不能睡)。

在进程上下文:10µs–20ms 用 usleep_range(比 msleep 精确),>20ms 用 msleep。 别用 mdelay 白白占着 CPU。

这条规则跟第 4 课的"能不能睡眠看上下文"是同一条铁律的应用。

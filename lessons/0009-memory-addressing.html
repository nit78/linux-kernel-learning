内存寻址:从虚拟地址到物理地址

内存管理篇开篇。这是驱动开发最硬核、对你价值最高的一篇。你写驱动每次 kzalloc、每次访问设备寄存器、每个 page fault, 底层都靠这课讲的机制。先把地基打好:CPU 发出的虚拟地址怎么变成物理地址? DRAM 和设备内存(MMIO)有什么区别?这是后面 §6 物理内存、§7 虚拟内存、§8 缺页的必备前置。

MCU 对照:你熟悉的"地址"在这里变了

裸机上你写的地址大多就是物理地址(直接指向 RAM 或外设寄存器)。x86/ARM 跑 Linux 时,CPU 发出的都是虚拟地址, 要经过 MMU + 页表翻译才到物理地址。这一层翻译就是本课主角。

§5.1 DRAM 与 MMIO:两种"物理内存"

关键认知:物理地址空间不是只有 RAM。它是统一的一张地址表,RAM(DRAM)和设备寄存器/显存(MMIO)都映射在里面,由 BIOS/UEFI 的内存表(E820/UEFI)标注各段类型:

物理地址空间(简化,实际由 BIOS/UEFI 表描述) 0xFFFF_FFFF_FFFF_FFFF ┌─────────────────────┐ │ ... │ │ MMIO: PCIe 设备 BAR │ ← GPU 显存、网卡寄存器、PCIe 配置空间 │ ... │ 这些地址落到设备,不在 DRAM 上! 0x0010_0000 ~────────┤ │ │ DRAM: 真正的内存条 │ ← 你的 8GB/16GB 物理内存 │ ... │ 0x0000_0000 ──────────┴─────────────────────┘ ← 1MB 以下还有 BIOS 保留区 CPU 给一个物理地址 → 总线决定它去 DRAM 还是去设备(MMIO)。 所以"访问 GPU 寄存器"和"访问内存",对 CPU 是同一套 load/store,只是地址段不同。

DRAM(主存)

真正的内存条。CPU 读写经缓存(L1/L2/L3),可乱序、可聚合。可缓存(cacheable)。

内核用 kmalloc/alloc_pages 分配的就是这种。

MMIO(内存映射 IO)

设备寄存器/显存,映射进物理地址空间。绝不能缓存——每次访问必须真实到达设备,顺序也要严格。

驱动必须用 ioremap() 建立带正确属性(uncached/强序)的映射,不能当普通指针解引用。

为什么 MMIO 不能当 DRAM 访问

若 CPU 把设备寄存器地址当 DRAM 缓存:读寄存器可能读到过期的缓存值(设备状态变了但 CPU 还看旧的); 写寄存器可能被缓存聚合/乱序(两条"置位"命令被合成一条,或顺序颠倒)。所以 ioremap 出来的映射标记为 uncached + 强序, 且必须用 readl/writel(带屏障的访问函数),不能用裸指针解引用。

§5.2.1 寻址:MMU + 多级页表

CPU 发出虚拟地址(VA),MMU(内存管理单元,硬件)负责把它翻译成物理地址(PA)。翻译规则存在页表里,页表是进程私有的。

页表是一棵"分级树"

虚拟地址按固定 bit 位切分成多段,每段作为一级索引去查页表树。x86_64 在 6.x 默认 5 级页表(LA57):

x86_64 5 级页表(LA57,57 位虚拟地址) 虚拟地址 57 位:[ 签名扩展 ][ PGD idx | P4D idx | PUD idx | PMD idx | PTE idx | 页内偏移 ] 9 9 9 9 9 12 (bit) CR3 ──→ PGD(每项 512GB) │ 按 PGD idx(9 bit)选一项 ↓ P4D(每项 512GB → 注:LA57 新增这一层) │ ↓ PUD(每项 1GB) │ ↓ PMD(每项 2MB) ← 若大页(2MB),到此为止 │ ↓ PTE(每项 4KB) ← 最终页,含物理页帧号 + 权限位 │ ↓ 物理地址 + 页内偏移 每级 9 bit → 512 项(2^9);页内偏移 12 bit → 4KB 页。 4 级(48 位)时没有 P4D,VA 空间 256TB;5 级(57 位)扩到 128PB。
页表级对应英文每项覆盖备注
PGDPage Global Directory512 GB(LA57)CR3 指向它,每个进程一份
P4DPage 4 Directory—5 级页表新增,4 级时折叠
PUDPage Upper Directory1 GB
PMDPage Middle Directory2 MB大页(2MB)在这层终止
PTEPage Table Entry4 KB最终表项:物理页帧号 + R/W/X 权限位
为什么分多级(而不是一张大表)?

一张覆盖 57 位空间的扁平页表会大到不可行(2^45 项 × 8 字节 = PB 级)。多级树让"没用的虚拟地址范围"不占物理内存—— 只有实际用到的区域,对应的页表分支才被创建。这是空间换时间的精妙设计。

版本纠偏:4 级还是 5 级?

老资料默认讲 4 级(48 位,256TB)。但6.x 在支持 LA57 的 CPU 上默认启用 5 级(57 位,128PB),多出 P4D 这一层。 你的 WSL2 是 6.6,很可能跑在 5 级模式(取决于底层 CPU)。内核引入 P4D 是为了"4 级/5 级可移植"—— 在 4 级 CPU 上 P4D 被折叠(相当于一层空操作)。可用 grep la57 /proc/cpuinfo 看 CPU 是否支持。 无论几级,翻译原理一样——多一级只是多查一次表。

MMU 与 TLB 的协作

每次访存都走 5 级树太慢(5 次内存读)。硬件用 TLB(Translation Lookaside Buffer) 缓存"VA→PA"翻译结果:

一次虚拟地址访问的完整流程 CPU 给出 VA │ ↓ TLB 查询(VA 的翻译在不在缓存里?) │ ├─ 命中(TLB hit) ──→ 直接拿到 PA,访存(快,这才是常态) │ └─ 未命中(TLB miss) │ ↓ MMU 硬件页表遍历(page table walk):按 PGD→P4D→PUD→PMD→PTE 逐级读内存 │ ├─ 找到 PTE,权限检查通过 → 把翻译填进 TLB,再访存 └─ PTE 无效/权限不符 → 触发缺页异常(第 12 课深讲),交给内核处理 TLB 是 CPU 内的硬件缓存,软件不可直接操作,只能"通知刷掉"(如进程切换、改页表时)。

TLB 的命中是性能关键——miss 要走 5 次内存的页表遍历。所以内核想方设法减少 TLB miss(大页、预取)和 TLB 刷新开销:

机制作用
PCID(进程上下文 ID)给 TLB 项打进程标签,进程切换时不必全刷 TLB(只有相同 PCID 的项才匹配)
KPTI(内核页表隔离)Meltdown 缓解:用户态/内核态用不同页表。代价是 CR3 切换变频繁,所以 PCID 变得更关键
大页(hugepage)2MB/1GB 页,一个 TLB 项覆盖更大范围,减少 TLB 压力

内核虚拟地址空间 vs 用户虚拟地址空间

每个进程有自己的页表,但所有进程共享同一份内核地址空间映射(高地址区段)。x86_64 概览(具体见 §7):

x86_64 虚拟地址空间划分(简化,§7 详讲) 高地址 ┌─────────────────────────┐ │ 内核空间(直接映射区/VMALLOC/FIXMAP...)│ ← 所有进程共享,高半区 │ │ 进程切换时这部分页表不变 ───────┤──────────────────────────┤ ← 不可访问的空洞(隔离用户与内核) │ │ │ 用户空间(代码/数据/堆/mmap/栈) │ ← 每个进程私有 低地址 └─────────────────────────┘

关键:内核代码访问的虚拟地址,要么在"内核空间"直接映射区,要么是 vmalloc/ioremap 动态映射的。 驱动里 kmalloc 返回的地址在直接映射区,ioremap 返回的在 VMALLOC 区。

§5.2.2 + §5.3 内存映射与 ioremap(GPU framebuffer 案例)

把上面的机制串起来——一个真实驱动场景:访问 GPU 的 framebuffer。

  1. GPU 通过 PCIe 暴露一段 BAR(Base Address Register),映射进物理地址空间的 MMIO 区(不是 DRAM)。
  2. 内核启动时从 BIOS/ACPI 知道这段物理地址范围。
  3. 驱动调 ioremap(phys, size) → 内核在内核虚拟地址空间建立一段映射,属性 uncached + 强序。
  4. 驱动拿这个虚拟地址,用 readl/writel/iowrite32 访问 → CPU 经 MMU 翻译 → 到达物理 MMIO 地址 → 总线转发给 GPU。
// 驱动访问 MMIO 寄存器的标准模式
void __iomem *regs = ioremap(pci_resource_start(pdev, 0),   // 物理 MMIO 地址
                              pci_resource_len(pdev, 0));
if (!regs) return -ENOMEM;

u32 ctrl = readl(regs + CTRL_REG);     // 读寄存器(带屏障,不缓存)
writel(ctrl | ENABLE, regs + CTRL_REG); // 写寄存器

iounmap(regs);                            // 释放映射
常见错误(面试常考)

不要把 ioremap 的返回值当普通指针解引用(*regs 或 regs[0])—— 它是 __iomem 地址,属性与 DRAM 不同,裸解引用会被 Sparse 检查器警告,且行为不可预测。 必须用 readl/writel/ioread32/iowrite32 等显式 IO 访问函数。

动手实验:看自己的页表与 CR3(WSL2 可跑)

内存寻址的硬件细节不能直接"写实验"测(MMU/TLB 是硬件),但你可以从内核和 /proc 观察页表的真实存在。 这实验纯观察,WSL2 完全可跑。

先声明:这实验在测什么

不是测性能,而是验证"页表真实存在、每进程独立、CR3 指向它"。你将看到自己的 bash 进程的页表基址、虚拟地址映射。 根据 LR-0012 规则:本实验不涉及"锁/竞争/性能",是观察性的。

  1. 看你的 CPU 是否支持 LA57(5 级页表): 
    grep la57 /proc/cpuinfo | head -1
# 有输出 = 支持 5 级;无输出 = 4 级
  2. 看当前进程(bash)的页表基址 CR3。内核把每个进程的 CR3 值(实际是 mm_struct 的 pgd)暴露在 /proc: 
    cat /proc/self/pagetable 2>/dev/null | head
# 或更直接,看 mm 的 pgd(需要 root 或内核 5.x+ 的 /proc/self/status)
grep -i pgd /proc/self/status 2>/dev/null
  3. 看一段虚拟地址的实际映射(以 bash 自身的代码段为例): 
    cat /proc/self/maps | head -3
# 输出形如:559c1a2b0000-559c1a2b3000 r--p ... /bin/bash
# 这是虚拟地址范围,后面权限 r--p 表示只读+私有
  4. 打开两个 bash(A 和 B),分别 cat /proc/self/maps | head -1 —— 你会发现两个进程的虚拟地址可以相同(都是 0x559c... 开头), 但它们映射到不同物理页。这就是"虚拟地址空间每进程独立、靠各自页表翻译"的可观察证据。
观察重点

不同进程的相同虚拟地址,映射到不同物理页——这正是"每进程一份页表"的直接证据。同一虚拟地址在 A 的页表里指向物理页 X, 在 B 的页表里指向物理页 Y。翻译完全由各自的页表(CR3)决定。这就是为什么进程间内存隔离能成立。

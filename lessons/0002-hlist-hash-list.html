hlist：哈希链表——为什么桶头少一个指针

第 1 课结尾留了个问题：hlist（哈希链表）为什么只比 list_head 少一个指针？ 这节课就拆它。你会顺带见识到内核里最巧妙的一次双指针用法—— 这是你在 MCU 裸机代码里几乎不会遇到的思维。

先建立直觉 内核里凡是"成千上万个、大多为空"的集合（比如哈希表的桶），都舍不得用两个指针做头。 hlist 就是给这种场景特制的链表。

问题：哈希表逼出来的设计

哈希表的本质是"一个数组 + 每个数组元素挂一条链"：

哈希表 = 桶数组 + 每个桶上挂一条冲突链 bucket[0] ─→ node ─→ node ─→ NULL bucket[1] ─→ NULL（空桶） bucket[2] ─→ node ─→ NULL bucket[3] ─→ NULL（空桶） ... bucket[N] ─→ node ─→ node ─→ node ─→ NULL 典型哈希表几千上万个桶，绝大多数是空桶。

如果桶头用 list_head（两个指针），那一个空桶就白占 16 字节（64 位）。 几千个桶下来，浪费相当可观。于是内核单独造了 hlist_head，桶头只留一个指针： 

// include/linux/types.h
struct hlist_head {
    struct hlist_node *first;    // 只有一个指针：指向桶里第一个节点
};

struct hlist_node {
    struct hlist_node *next;
    struct hlist_node **pprev;   // ← 注意：双指针！不是 *prev
};

对比一下两者代价：

对比项list_head（双向循环）hlist（哈希单链）
头节点大小 next + prev = 2 个指针 first = 1 个指针
每个节点大小 next + prev = 2 个指针 next + pprev = 2 个指针（一样）
能否双向遍历 能（循环） 能（靠 pprev）
典型用途 通用双向链表 哈希桶头（成千上万个）

节省只发生在桶头上，但哈希表里桶头数量远多于实际节点（多数桶空着），所以总账很划算。

精髓：pprev 为什么是双指针

这是这节课最难、也最值的一点。慢慢看。

在 list_head 里，prev 指向"前一个节点"。但 hlist 的桶头是 hlist_head 类型，节点是 hlist_node 类型——类型不一样。 如果第一个节点的 prev 想指回桶头，它存什么？存 hlist_head* 吗？ 那它就和其他节点（存 hlist_node*）类型不一致，每次删除都得判断"我是不是第一个节点"。

内核的解法极其优雅：让 pprev 不存"前一个节点的地址"，而存"前一个节点里那个指向我的指针字段的地址"。

第一个节点：pprev 指向桶头的 first 字段 hlist_head hlist_node(第一个) hlist_node(第二个) ┌──────────┐ ┌──────────────┐ ┌──────────────┐ │ first ─────────────→ next ──────────→ next ─→ ... │ │ │ │ │ │ │ │ │ pprev ────────┐ │ │ pprev ──────────────┐ └──────────┘ └──────────────┘ └──────────────┘ │ ↑ 指向 &head->first │ └──────────────────────────────┘ ↑ 指向 &prev->next
关键洞察：无论是不是第一个节点，pprev 都指向"指向前一个链域的地址" 情况 A（桶中第一个节点）： node->pprev == &head->first // 指向桶头的 first 字段 情况 B（桶中非第一个节点）： node->pprev == &prev->next // 指向前一个节点的 next 字段 两种情况下 *node->pprev 都等于 node 本身——这正是统一的来源。

统一删除：双指针的回报

这就是 **pprev 换来的核心收益：删除任意节点只需一行，无需特判桶头。 

// 删除一个 hlist 节点（include/linux/list.h 简化版）
static inline void hlist_del(struct hlist_node *n)
{
    struct hlist_node *next = n->next;
    struct hlist_node **pprev = n->pprev;

    // *pprev 就是"指向我的那个指针"——写它就把我从链上摘掉
    *pprev = next;              // 前一个链域，改成指向我的下一个
    if (next)
        next->pprev = pprev;   // 让下一个回指到前一个链域
}

对比如果用单指针 prev 会怎样：

若用 *prev（朴素做法）

删除中间节点：OK，prev->next = next; next->prev = prev;

删除第一个节点：炸了——prev 此时指向桶头（不同类型）， 要 head->first = next，必须 if 判断是不是第一个。

结果：每个删除函数里都要写两套分支。

用 **pprev（内核做法）

无论哪个节点：*pprev = next; 一行搞定。

因为 pprev 已经是"指向我的指针的地址"—— 对它解引用并赋值，就改掉了前一个链域。

结果：无分支，O(1) 删除，代码简洁不易错。

给 C 工程师的提醒 这是"指针的指针"的教科书级用例：当你需要对一组"名字不同、类型不同、但语义相同"的指针字段做统一操作时， 用 ** 拍平它们。内核源码里这类手法反复出现（页表、VFS 路径查找都用到类似思想）。

常用 API

API做什么
HLIST_HEAD(name)声明并初始化一个 hlist 头（静态）。
hlist_add_head(&node, &head)把节点插到桶头（最常用）。
hlist_add_behind(&prev, &node)插到某节点之后。
hlist_del(&node)摘除节点（一行式统一删除）。
hlist_for_each_entry(item, &head, member)遍历桶中所有节点，自动用 container_of 取宿主。

你会发现这些 API 和 list_* 几乎一一对应——内核设计 API 时刻意保持了一致性。 会了 list_head，hlist 的学习成本主要就集中在"理解 pprev"上。

动手实验：一个迷你哈希表

目标：用内核提供的 DECLARE_HASHTABLE 宏 建一个 8 个桶的小哈希表，存 5 个"蓝牙设备"，按地址哈希分散到桶里，加载时打印每个桶的内容。 这恰好是你做 WiFi/蓝牙驱动时遇到的"按地址查设备"的真实结构。

前提 内核哈希表 API 在 linux/hashtable.h（Linux 3.97+ 标准，你的 6.6.87.2 当然支持）。 你已经在 ../doc/WSL2内核编译与驱动环境搭建.md 里把内核编译 + /lib/modules/$(uname -r)/build 软链都弄好了， 直接复用那个环境即可——这节课的 .ko 是纯软件模块，WSL2 完全能加载运行。

关于代码风格的一个小说明：你在第 1 课的 bt_list.c 里用了 uint16_t（stdint 风格）， 这能跑。但内核源码惯例是用 linux/types.h 里的 u8/u16/u32/u64（还有 __u32 用于用户可见的 ABI）。 本课示例统一用内核风格的 u16——读内核源码时你看到的也全是这个。两套在模块里都合法，但熟悉内核那套能让你读源码更顺。

① 源码 bt_hash.c

// bt_hash.c — 第 2 课实验：用 hlist 哈希表管理蓝牙设备
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/list.h>        // hlist 在这里
#include <linux/hashtable.h>  // DECLARE_HASHTABLE / hash_add / hash_for_each
#include <linux/slab.h>
#include <linux/random.h>

struct bt_device {
    u16               addr;
    char              name[16];
    struct hlist_node node;     // ← 嵌入 hlist 节点
};

// 声明一个 8 桶哈希表（桶数必须是 2 的幂）
static DECLARE_HASHTABLE(bt_table, 3);   // 2^3 = 8 个桶

static int __init bt_hash_init(void)
{
    int i;
    struct bt_device *dev;
    u16 addrs[] = { 0x1122, 0x3344, 0x5566, 0x7788, 0x1122 + 0x8 }; // 故意制造一些冲突

    pr_info("bt_hash: 加载\n");

    for (i = 0; i < 5; i++) {
        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (!dev) return -ENOMEM;
        dev->addr = addrs[i];
        scnprintf(dev->name, sizeof(dev->name), "BT-%d", i);

        // 关键：按 addr 哈希，挂进对应桶。hash_32 把值映射到 [0, 桶数)。
        hash_add(bt_table, &dev->node, dev->addr);
    }

    // 遍历整个哈希表，逐桶打印
    struct bt_device *cur;
    int bkt;
    pr_info("bt_hash: 哈希表内容:\n");
    hash_for_each(bt_table, bkt, cur, node) {
        pr_info("  bucket[%d] - %s (addr=0x%04x)\n", bkt, cur->name, cur->addr);
    }
    return 0;
}

static void __exit bt_hash_exit(void)
{
    int bkt;
    struct bt_device *cur;
    struct hlist_node *tmp;

    // 边遍历边删，必须用 _safe 版本（桶里是 hlist）
    hash_for_each_safe(bt_table, bkt, tmp, cur, node) {
        pr_info("bt_hash: 删除 %s\n", cur->name);
        hash_del(&cur->node);
        kfree(cur);
    }
    pr_info("bt_hash: 卸载\n");
}

module_init(bt_hash_init);
module_exit(bt_hash_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 2: hlist hash table demo");

② 跑起来

  1. 编译：make（复用第 1 课的 Makefile，把 obj-m 改成 bt_hash.o）
  2. 加载：sudo insmod bt_hash.ko
  3. 看桶分布：dmesg | tail —— 你会看到 5 个设备散落在 8 个桶中，地址相近的可能撞到同桶
  4. 卸载：sudo rmmod bt_hash
观察重点 用 dmesg 输出对照地址 0x1122 和 0x1122 + 0x8—— 它们哈希到同一个桶的概率应该较高。这正是哈希冲突的真实样子， 冲突时一个桶里就是一条 hlist 冲突链。看到它，你就理解了 hlist 存在的全部理由。

接下来

到这里，你掌握了内核的两种主力链表：list_head（通用双向）和 hlist（哈希专用）。 它们覆盖了内核里"线性关系"的绝大部分场景。

但内核里还有一类"有序关系"场景——需要快速查找/插入/删除的有序集合， 链表做不到（O(n)），这时内核用红黑树（rbtree）。 这就是第 3 课的主题：CFS 完全公平调度器、ext4 区段树都用它。

推荐精读 主教材《图解Linux内核》§2.1「关系型数据结构」（同章其余小节）。 英文权威：LWN 经典文章 "Linux kernel design patterns - part 2"（Neil Brown）—— 它正好有一节专门讲 hlist 为何省一个指针，与本课对照极佳。

中断与延迟执行：从 MCU ISR 到内核的"上下文分工"

这是你的 MCU 经验大规模迁移的一课。裸机里你写 ISR,内核里你也写 ISR—— 但内核多了一层必须理解的分工:上半部 / 下半部。 不懂它,后面所有驱动(包括你移植过的蓝牙/WiFi)都只能停在"照搬"层面。

本课的两个版本纠偏 老书/老博客常讲 tasklet,但6.6 起 tasklet 已废弃(2024 "end of tasklets" 计划)。 本课会告诉你现状,并给你该用的替代。request_irq 自 4.5 起其实只是 request_threaded_irq 的包装——这两个点很多人讲错。

为什么内核要拆"两半"

先回到你熟悉的 MCU 场景,做一次对照:

MCU / 裸机 ISR

硬件触发 → CPU 跳进你的 ISR → 你在 ISR 里把事干完(读寄存器、清标志、更新状态、可能还塞个队列)→ 返回。

整个过程中,通常中断是关着的(或同级中断被屏蔽)。ISR 干多久,别的中断就等多久。

所以你被训练成:ISR 越短越好,绝不调用阻塞函数。

Linux 内核 ISR

同样的约束依然成立(甚至更严):硬中断 ISR 跑在"中断上下文",不能睡眠、不能持有锁等很久。

但内核要处理的事很多(I/O 协议栈、唤醒进程、网络栈),塞进 ISR 会把所有中断延迟拖死。

内核的解法:ISR 只做最紧急的几纳秒,剩下的活推迟到"下半部"——开中断后再慢慢干。

于是内核的中断处理在时间轴上分成两段:

一次设备中断的时间轴 时间 ──────────────────────────────────────────────────────→ ┌─────────────────┐ ╔═════════════════════════╗ │ 上半部 (硬中断 ISR) │ ║ 下半部 (延迟执行) ║ │ - 应答中断 │ ║ - 协议解析、唤醒进程 ║ │ - 拷贝数据到 RAM │ ║ - 访问可能睡眠的资源 ║ │ - 不可睡眠 │ ║ - 可睡眠(取决于机制) ║ │ - 中断(部分)关闭 │ ║ - 中断已重新打开 ║ └─────────────────┘ ╚═════════════════════════╝ ↑ irq_handler() ↑ softirq / workqueue / thread_fn ISR 极短 → 尽快重新开中断 → 系统响应能力不被拖垮。

这就是"为什么拆"的根本原因:让 CPU 尽快回到"能接受新中断"的状态。 上半部越短,中断延迟越低,实时性越好。下半部承担"重活",且可以选择在更宽松的环境里跑。

下半部的四种机制

这是本课的"选型表",你以后写驱动反复要回来查。内核给了四种延迟执行机制,各有能力边界:

机制API运行上下文能睡眠?何时用
softirq open_softirq / raise_softirq 中断上下文(软中断) 否 极低延迟、高频、且对时序敏感的内核子系统(网络 TX/RX、RCU、定时器)。驱动极少自己开 softirq——只有编译期固定的几种。
tasklet
⚠ 已废弃		 DECLARE_TASKLET 等 中断上下文(建在 softirq 之上) 否 新代码不要用。移植老驱动会看到。替代:workqueue 或 threaded IRQ。
workqueue alloc_workqueue / INIT_WORK / queue_work 进程上下文(内核线程) 能 需要睡眠、分配内存、持有互斥锁、做 I/O 的"下半部"。驱动最常用。
threaded IRQ request_threaded_irq hardirq 只做最少事 + 内核线程 能(在线程里) 中断处理本身就需要睡眠(如 I²C/SPI 总线读寄存器)的场景。现代驱动首选。
关于 tasklet 的真相(6.6 现状)

tasklet 自 2024 年起正式废弃(LWN: The end of tasklets)。 内核正在把所有 in-tree 驱动从 tasklet 迁到 BH workqueue 或 threaded IRQ。 tasklet 建在 softirq 之上(占用两个 softirq 向量),但softirq 本身不在移除清单—— 被废弃的是 tasklet 这一层 API,不是 softirq。

给你的实操建议:

  • 读老驱动(尤其 5.x 之前)大量见到 tasklet——要能看懂,知道它在 softirq 里跑、不能睡眠。
  • 自己写新驱动:别用 tasklet。需要睡眠 → workqueue 或 threaded IRQ;不需要睡眠、追求低延迟 → 考虑 softirq(但驱动很少自己开)。

铁律:能不能睡觉,看"上下文"

整章的精华,浓缩成一张判断表。以后你写驱动调任何 API 前,先问"我现在在什么上下文":

上下文典型入口能睡眠?能持有 mutex?
硬中断(top half / hardirq)irq_handler_t❌ 绝不❌
软中断(softirq / tasklet / NAPI)softirq 回调、tasklet func❌❌(只能用 spinlock)
进程上下文(workqueue / 线程化 IRQ / 系统调用)work_func、thread_fn、syscall✅ 可以✅
为什么硬中断不能睡眠

睡眠 = 让出 CPU 等某个事件(如 I/O 完成)。但硬中断不属于任何进程,调度器没有可"挂起"的对象; 而且睡眠会让中断长期关着,整个系统的中断响应崩盘。这条规则没有例外,违反了就是 oops/死锁。

这也解释了为什么 workqueue/threaded IRQ 这么重要:它们在进程上下文跑,把"中断触发的重活"搬进能睡眠的世界。

小心陷阱:"上下文"这个词有两层含义

很多人卡在这一步:"hardirq 和 softirq 栈相同、寄存器相同、特权级相同,凭什么是两个上下文?" 卡住的原因是——你脑子里的"上下文"和内核说的"上下文"是两个不同的东西,只是中文恰好都叫"上下文"。

 硬件上下文 (hardware context)执行上下文 (execution context)
是什么CPU 物理执行环境内核的软件标记
组成寄存器 / 栈 / 特权级(ring 0/3) / 页表preempt_count 位域 + current
谁切换调度器(context_switch)中断进入/退出代码
切换成本高(存全套寄存器)极低(改几个 bit)
用来干嘛进程切换时保存/恢复判断"这段代码能睡眠吗、能持什么锁"
"能不能睡觉"——这才是内核区分上下文的唯一理由

寄存器、栈、特权级都是中性的物理状态,本身没有"能不能睡眠"这种属性。内核需要知道"现在这段代码属于哪种执行域、受什么规则约束", 于是发明了执行上下文——一个软件层标签,记录在 thread_info->preempt_count 的不同 bit 上。

判断"当前是什么上下文"靠的就是查这些 bit:

in_irq()     = (preempt_count & HARDIRQ_MASK) != 0   // hardirq 位
in_softirq() = (preempt_count & SOFTIRQ_MASK) != 0   // softirq 位
// 两者都为 0,且 current 指向真实进程 → 进程上下文

hardirq 和 softirq 之所以是两个上下文,靠的不是栈/寄存器,而是 preempt_count 上不同的 bit。

一个具体问题:softirq 跑的时候,上下文到底是什么?

softirq 有两种触发路径。注意对比右边——执行上下文相同,但硬件上下文不同。

路径 A · 常见

hardirq 退出时跑

进程 a.out │ 硬中断 ▼ handler() │ irq_exit() ▼ __do_softirq()

执行上下文 = softirq (SOFTIRQ 位 = 1)

硬件上下文 = 被中断的 a.out 的

current 还指向 a.out

路径 B · 兜底

ksoftirqd 内核线程里跑

ksoftirqd 线程 │ 被调度器选中 ▼ __do_softirq()

执行上下文 = softirq (SOFTIRQ 位 = 1)

硬件上下文 = ksoftirqd 自己的

current = ksoftirqd

结论:同一种执行上下文(softirq),却有两种硬件上下文。 你用"硬件上下文"模型去理解"执行上下文",当然觉得矛盾——因为它们根本是两层不同的概念。
认知升级口诀

以后在内核里看到"上下文",先问自己:

  • 这里说的是硬件上下文吗?(进程切换语境 → 寄存器/栈/特权级)
  • 还是执行上下文?(中断/睡眠语境 → preempt_count + current)

这是内核术语的一个历史包袱,英文也容易混:context_switch 指前者,in_interrupt() 判断的是后者。不是你理解错了,是同一个词被用在了两层意思上。

真实 API:注册中断

// include/linux/interrupt.h
int request_threaded_irq(unsigned int irq,
                          irq_handler_t handler,      // 上半部(可为 NULL)
                          irq_handler_t thread_fn,    // 下半部线程函数
                          unsigned long irqflags,
                          const char *devname,
                          void *dev_id);

// 你熟悉的 request_irq 其实是它的包装(自 ~4.5 起):
static inline int __must_check
request_irq(unsigned int irq, irq_handler_t handler,
            unsigned long flags, const char *name, void *dev)
{
    return request_threaded_irq(irq, handler, NULL, flags, name, dev);
                                                    ↑↑↑ thread_fn=NULL → 不线程化
}

线程化中断的执行流程,画出来就懂:

request_threaded_irq 的一次中断处理 硬件中断 ──→ [handler 上半部] 只做:屏蔽本中断 + 唤醒内核线程 + 返回 IRQ_WAKE_THREAD │ ↓ (中断立即重新打开,系统照常响应别的中断) [thread_fn 下半部] 在专属内核线程里跑,可睡眠、可持有 mutex、可做 I/O │ ↓ 处理完毕,清除中断屏蔽,等下次 关键收益:中断被屏蔽的时间 = handler 那"几纳秒",而不是整个处理时间。

handler / thread_fn 的返回值(常考点)

返回值含义
IRQ_HANDLED处理完了。
IRQ_NONE不是我的中断(共享中断时用来统计噪声)。
IRQ_WAKE_THREAD上半部专用:告诉子系统"去调度我的 thread_fn"。线程化 IRQ 的标准返回。

动手实验:workqueue 自调度(WSL2 可跑)

关于 WSL2 的限制(诚实声明)

你的环境是 WSL2 + 6.6.87.2——没有真实硬件中断,不能注册一个 GPIO/PCI 中断然后等它触发。 所以本课实验不模拟硬件中断,而是聚焦在下半部机制本身:用 workqueue 做周期性任务 + 自调度, 这是你在驱动里反复要写的模式(中断来一次 → work 排一次 → work 里又把自己排进去做下一轮)。

真实硬件 IRQ 的实验(注册 GPIO 中断、用 request_threaded_irq 处理真实设备)需要真机或带 USB 透传的虚拟机——留给以后。

实验目标:写一个 .ko,加载时启动一个 workqueue 延迟任务,它每秒把自己重排一次,打印计数,共跑 5 次后自停。你会亲手用到 alloc_workqueue / INIT_DELAYED_WORK / queue_delayed_work。

// bt_work.c — 第 4 课实验:workqueue 延迟自调度(WSL2 可跑)
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/workqueue.h>

static struct workqueue_struct *bt_wq;
static struct delayed_work      bt_dwork;
static unsigned int               bt_tick;

/* 下半部函数:跑在进程上下文,可以睡眠(这里不睡,只演示) */
static void bt_work_fn(struct work_struct *work)
{
    bt_tick++;
    pr_info("bt_work: tick %u (跑在进程上下文,pid=%d,可睡眠)\n",
            bt_tick, current->pid);

    if (bt_tick < 5) {
        /* 自调度:1 秒后再排一次自己 */
        queue_delayed_work(bt_wq, &bt_dwork, msecs_to_jiffies(1000));
    } else {
        pr_info("bt_work: 完成 5 轮,停止自调度\n");
    }
}

static int __init bt_work_init(void)
{
    pr_info("bt_work: 加载\n");
    bt_wq = alloc_workqueue("bt_wq", 0, 0);   // 0,0 = 默认 flags + 默认 max_active
    if (!bt_wq) return -ENOMEM;

    INIT_DELAYED_WORK(&bt_dwork, bt_work_fn);
    bt_tick = 0;
    queue_delayed_work(bt_wq, &bt_dwork, msecs_to_jiffies(1000));  // 1 秒后启动
    return 0;
}

static void __exit bt_work_exit(void)
{
    /* 卸载前必须取消未决的 work,否则 work_func 访问已释放的资源会 oops */
    cancel_delayed_work_sync(&bt_dwork);
    destroy_workqueue(bt_wq);
    pr_info("bt_work: 卸载\n");
}

module_init(bt_work_init);
module_exit(bt_work_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 4: workqueue self-rescheduling demo");

跑起来(Makefile 同前几课,obj-m := bt_work.o):

  1. make → bt_work.ko
  2. sudo insmod bt_work.ko
  3. 等 5 秒,期间 dmesg | tail 观察:应看到每秒一条 tick,共 5 条,然后"完成 5 轮"
  4. 注意 pid:work 函数的 current->pid 是 bt_wq 这个内核线程的 pid,不是 insmod 进程——这就是"进程上下文"的可观察证据
  5. sudo rmmod bt_work
观察重点(也是真正的学习点)

1. current->pid 不是 insmod 的 pid —— 说明 work 函数确实跑在一个独立的内核线程里(进程上下文),而非调用者上下文。 这是你以后理解"中断下半部为何能睡眠"的第一手证据。

2. cancel_delayed_work_sync 不能省 —— 卸载时若 work 正在排队或执行,不取消就 destroy_workqueue, work 醒来访问已释放代码 = oops。这个取消模式你以后在所有驱动 remove 路径都会写。

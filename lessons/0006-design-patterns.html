内核设计模式：模板方法与观察者

内核是 C 写的,但到处是"设计模式"。这课讲贯穿全书、你在后续每一篇都会撞见的两个: 模板方法(VFS 的 file_operations)和观察者(通知链)。 学完它们,你读驱动代码时那些"一坨函数指针"和"xxx_notify"就都有了名字。

这课的连接点 模板方法的核心载体是 struct file_operations——一个函数指针表。 而"函数指针表 + 嵌入式结构体"正是第 1 课侵入式数据结构的延伸:数据结构里嵌入"行为"。 两个模式都会用到你已经熟悉的 container_of。

§2.2.1 模板方法设计模式

一句话:有一个固定的流程骨架(模板),具体步骤的实现交给使用者填。 内核管流程,使用者管细节。

本书 §2.2.1 用"做菜"做比喻:三步固定流程(备菜→加工→盛出)是模板,刀&锅 vs 蒸笼只决定每步怎么做。 内核里的真实落地是 VFS + file_operations:

用户调用 mmap() 时的模板方法 【模板骨架 = VFS 通用流程】 【具体步骤 = 驱动/文件系统填】 sys_mmap (内核) file_operations { ├─ 检查参数、准备 VMA .mmap = ext4_mmap, ← 各家自己实现 ├─ 调用 file->f_op->mmap() ────→ .read = ..., │ (模板在这里"调用使用者填的步骤") .write = ..., ├─ 安装映射到进程地址空间 .fault = ..., ← 缺页时才分配物理页 └─ 返回 .release = ..., } VFS 决定"mmap 这件事分几步、按什么顺序"; ext4 / 你的驱动只决定"其中某一步具体怎么做"。

真实定义就是一个全函数指针的结构体:

// include/linux/fs.h (简化)
struct file_operations {
    int    (*open)   (struct inode *, struct file *);
    ssize_t (*read)   (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)  (struct file *, const char __user *, size_t, loff_t *);
    int    (*mmap)   (struct file *, struct vm_area_struct *);
    int    (*release)(struct inode *, struct file *);
    /* 几十个函数指针 … */
};

// 一个真实的"填表":ext4 把自己的实现填进模板
static const struct file_operations ext4_file_operations = {
    .read_iter = ext4_file_read_iter,
    .write_iter= ext4_file_write_iter,
    .mmap      = ext4_file_mmap,
    .open      = ext4_file_open,
    .release   = ext4_release_file,
    /* … */
};
本质:函数指针表 = C 版的"接口/虚函数"

面向对象语言里这叫"接口 + 多态":VFS 定义接口(file_operations), 各文件系统提供实现(ext4 / sysfs / proc 各填一份)。用 C 也能写出面向对象—— 函数指针表 + 结构体就是 C 的虚函数表。读内核时遇到"xxx_op / xxx_ops" 命名的结构体,十有八九就是模板方法。

进阶:mmap 不分配物理页,fault 才分配

模板方法在 mmap 这里有个精彩细节,也是本书 §17 + §8 缺页异常的伏笔:

直觉但不对

mmap 调用时,立刻把物理内存分配好、映射进页表。

问题:映射 1GB 只读 1KB,却分配 1GB 物理页——巨大浪费。

内核实际做法(懒分配)

mmap 只登记一段虚拟地址区间(VMA),不分配物理页。

进程真去访问时 → 触发缺页异常 → 内核调用 vm_ops->fault() → 此时才分配那一页物理内存。

所以 mmap 这个"模板"分两段:f_op->mmap(登记 VMA) + vm_ops->fault(缺页时填页)。后者也是一个函数指针表:

// include/linux/mm.h (简化) — VMA 的操作表,另一组"模板"
struct vm_operations_struct {
    int (*open)(struct vm_area_struct *);
    vm_fault_t (*fault)(struct vm_fault *);   // ← 缺页时被调
    void (*close)(struct vm_area_struct *);
};
版本纠偏:mmap file 操作正在退场(6.x)

老资料都说"驱动填 f_op->mmap"。6.x 起,这个回调正在被废弃: LWN 2024 文章 The phaseout of the mmap() file operation 说明 VFS 改用新的 mmap_prepare 回调 + 基于 fault 的模型。 驱动应迁到新接口。读老驱动仍会见到旧 mmap,要能看懂; 写新驱动要看 官方 mmap_prepare 文档。

但模式没变——还是"VFS 管流程,驱动填某一步"。变的只是填哪个槽。

§2.2.2 观察者设计模式

一句话:被观察者维护一个订阅者列表,有事时统一通知列表上的每个人;观察者不用轮询。 解耦"事件源"和"关心事件的人"。

本书 §2.2.2 用"订报纸"比喻:报社(被观察者)维护订阅列表,新报印好按列表派送;读者(观察者)不必天天跑去问。 内核里的落地是通知链(notifier chain)。看到 xxx_notify 多半是被观察者, xxx_listener / register_xxx_notifier 多半是观察者。

核心数据结构:订阅链 + 回调

// include/linux/notifier.h (简化)
struct notifier_block {
    notifier_fn_t notifier_call;   // 观察者的回调函数
    struct notifier_block *next; // 串成链(又见 list!)— 单链即可
    int priority;                 // 优先级,高的先收到
};

// 回调签名:val 是事件类型,v 是事件数据
typedef int (*notifier_fn_t)(struct notifier_block *nb,
                            unsigned long val, void *v);

四种变体,差别在用什么锁、能在什么上下文调用(又见第 4 课的上下文铁律):

变体头类型锁回调上下文能睡眠?
Blockingblocking_notifier_headrwsem进程✅ 能
Atomicatomic_notifier_headspinlock中断/原子❌ 不能
SRCUsrcu_notifier_headSRCU进程✅ 能
Rawraw_notifier_head无(调用者自管)任意取决于调用者

选哪个? 看事件源在什么上下文发通知、回调要不要睡眠。 最常用 Blocking(进程上下文、可睡眠)。本书 §2.2.2 提到的观察者模式,绝大多数用 blocking notifier 实现。

通知链的两端 【被观察者(发布者)】 【观察者(订阅者)】 static BLOCKING_NOTIFIER_HEAD(evt_list); static int my_cb(struct notifier_block *nb, unsigned long val, void *v) { // 有事时: pr_info("事件 %lu\n", val); blocking_notifier_call_chain(&evt_list, return NOTIFY_OK; EVT_FOO, data); } static struct notifier_block my_nb = { // 内核遍历链,逐个调 notifier_call .notifier_call = my_cb, }; // 订阅: blocking_notifier_chain_register(&evt_list, &my_nb);

回调的返回值控制链的遍历:

返回值含义
NOTIFY_OK处理了,继续通知下一个。
NOTIFY_DONE不关心,继续。
NOTIFY_STOP停止通知后续。
NOTIFY_BAD出错,停止。

动手实验:module 通知链(WSL2 可跑)

这个实验特别精彩——它是自观察的:你的模块注册成观察者, 监听"别的模块被加载/卸载"这个事件。加载实验模块后,你再 加载第 1 课的 bt_list.ko, 就能从 dmesg 看到"模块加载"事件被你的观察者捕获。模板方法和观察者都用 container_of 串结构体——你会再次见到第 1 课的手法。 

// bt_observer.c — 第 6 课实验:观察 module 加载/卸载事件
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/notifier.h>

/* 观察者回调:有模块状态变化时被调用 */
static int bt_module_event(struct notifier_block *nb,
                          unsigned long action, void *data)
{
    struct module *mod = data;

    switch (action) {
    case MODULE_STATE_LIVE:    // 完全加载成功
        pr_info("bt_obs: 模块加载完成 [%s]\n", mod->name);
        break;
    case MODULE_STATE_GOING:   // 正在卸载
        pr_info("bt_obs: 模块正在卸载 [%s]\n", mod->name);
        break;
    default:
        break;   // MODULE_STATE_COMING 等,这里不打印
    }
    return NOTIFY_OK;
}

/* 订阅块:把回调填进 notifier_block(模板方法!) */
static struct notifier_block bt_nb = {
    .notifier_call = bt_module_event,
    .priority       = 0,
};

static int __init bt_obs_init(void)
{
    int ret = register_module_notifier(&bt_nb);
    pr_info("bt_obs: 已注册模块通知链观察者 (ret=%d)\n", ret);
    return ret;
}

static void __exit bt_obs_exit(void)
{
    unregister_module_notifier(&bt_nb);
    pr_info("bt_obs: 已注销\n");
}

module_init(bt_obs_init);
module_exit(bt_obs_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 6: observer pattern via module notifier");

跑起来 + 触发事件(Makefile 同前,obj-m := bt_observer.o):

  1. make → bt_observer.ko
  2. sudo insmod bt_observer.ko —— 观察者上线
  3. sudo insmod bt_list.ko —— 关键:加载第 1 课那个模块,触发"模块加载"事件
  4. dmesg | tail —— 应看到 bt_obs: 模块加载完成 [bt_list]。你的观察者捕获到了别人被加载!
  5. sudo rmmod bt_list —— 应看到 bt_obs: 模块正在卸载 [bt_list]
  6. sudo rmmod bt_observer —— 观察者下线
两个模式一次看到

这个实验同时演示了两个模式:

  • 观察者:你的模块订阅事件,内核(kernel/module.c)在别人加载/卸载时调用你的回调。你没轮询——是被动收到通知。
  • 模板方法:你把 bt_module_event 填进 notifier_block.notifier_call(函数指针表),内核的 notifier_call_chain 负责"遍历链、逐个调用"——流程归它,你的实现填进槽里。

检验理解

file_operations 在 VFS 里扮演的角色,最准确的描述是?

内核的通知链(notifier chain)实现了观察者模式,它最核心的收益是?

接下来

这两个模式你会在后续每一篇反复撞见:file_operations(文件系统篇)、 vm_operations_struct(内存篇的缺页)、net_device_ops(网络)、 device_driver 的 probe/remove(综合应用篇的驱动模型)——全是模板方法。 而 CPU 热插拔、网络设备注册、reboot、panic 通知——全是观察者。有了名字,代码就不再是一坨函数指针。

红黑树（rbtree）：内核里的"有序集合"

链表（list_head）和哈希链表（hlist）解决的是"串起来"和"按桶找"。 但内核里还有一类场景:按大小排序、要快速插入/删除/查找最值——链表的 O(n) 查找撑不住, 这时内核用红黑树。这节课讲清它的原理,再用真实的 struct rb_node 动手。

为什么红黑树,不是 AVL、不是跳表 红黑树在"平衡程度"和"调整代价"之间取了工程上的甜点:插入/删除最多 3 次旋转就能恢复平衡, 比严格平衡的 AVL 调整更省。内核要的是最坏情况可控、均摊开销低,红黑树正合适。

原理:红黑树的 5 条性质

红黑树是一棵自平衡二叉搜索树,每个节点带一个颜色(红/黑)。它靠 5 条性质保证"没有一条路径会比另一条长两倍以上",于是查找/插入/删除都是 O(log n):

  1. 每个节点是红或黑。
  2. 根是黑的。
  3. 每个叶子(这里的叶子指 NULL 空节点)是黑的。
  4. 红节点的孩子必须是黑的——即不能有两个连续的红节点(红节点不挨着)。
  5. 从任一节点到其所有后代叶子的路径上黑节点数量相同。这个数量叫该节点的黑高。

第 4、5 条是核心。它们联手的效果:最长路径(红黑交替)最多是最短路径(全黑)的两倍。

一棵合法的红黑树(R=红, B=黑)。注意每条根→叶路径黑节点数都是 2。 (13 B) / \ (8 R) (17 R) / \ / \ (1 B) (11 B) (15 B) (25 B) / (22 R) 根→1: B → 1 个黑节点(根本身) + 1(叶子) = 黑高 2 根→22→叶: B-R-B-叶 = 黑高 2 ✓ 没有两个红相邻;每条路径黑节点数相等。
旋转,直觉版 插入/删除后如果违反了性质 4 或 5,就用左旋 / 右旋把树重新摆平衡。 旋转不改变二叉搜索树的"中序有序"性质——这是它能用来修复红黑树的前提。 本课不背旋转的 3 种 case,你只要记住:内核已经帮你写好了(rb_insert_color / rb_erase), 你要做的是按规则插入,剩下交给它。

内核 rbtree 的"半成品"设计

这是读内核代码必须先知道的一件事,很多人卡在这里:

你期待的通用库

像 C++ STL 的 std::map:insert(key, value)、find(key),一键搞定。

比较函数由模板参数固定,数据和节点由库管理。

内核 rbtree 实际提供

只给节点 + 平衡算法。rb_node 同样是侵入式的(嵌进你的结构体)。

比较、查找、插入位置你自己写——内核只负责插入后的重新着色和旋转(rb_insert_color)。

真实定义非常小:

// include/linux/rbtree_types.h
struct rb_node {
    unsigned long  __rb_parent_color;  // 把"父指针 + 颜色"塞进一个字
    struct rb_node *rb_right;
    struct rb_node *rb_left;
} __attribute__((aligned(sizeof(long))));

struct rb_root {
    struct rb_node *rb_node;
};

#define RB_ROOT  (struct rb_root) { NULL, }  // 空树
那个 __rb_parent_color 很妙 节点的"颜色"只是 1 bit,单独存太浪费。内核把父节点指针的最低位当颜色位用 (因为 rb_node 用 aligned(sizeof(long)) 对齐,指针低 1~3 位永远是 0,可以拿来存 bit)。 一个字既存父指针又存颜色——这是用空间对齐特性省内存的经典手法,你在内核里会反复见到类似套路。

为什么要你"自己写插入比较"?因为泛型代价高。 不同子系统对"键怎么比较"千差万别 (调度器比 vruntime、ext4 比磁盘块号、定时器比到期时间)。内核宁可让每个使用者写十几行比较循环, 也不强行抽象出一个带函数指针的泛型树——省掉一次间接调用,在热路径上值得。

核心 API:插入 / 删除 / 遍历

API做什么
RB_ROOT声明一棵空树(struct rb_root root = RB_ROOT;)。
rb_link_node(node, parent, &link)把新节点挂到树形结构上(还没平衡)。你先自己遍历找到插入位置 parent 和挂载点 link。
rb_insert_color(node, root)对刚 rb_link_node 的节点做重新着色 + 旋转恢复红黑性质。两步合起来才是一次完整插入。
rb_erase(node, root)删除节点(含自动再平衡)。
rb_first(root) / rb_last(root)取最小 / 最大节点——O(log n) 直奔最左 / 最右。
rb_next(node) / rb_prev(node)中序遍历的后继 / 前驱——按排序顺序走。

插入一个节点的标准骨架(你以后会在内核里反复看到这个模式):

// 向 root 中按 key 插入 data->node。自定义比较。
static void my_insert(struct rb_root *root, struct my_type *data)
{
    struct rb_node **new  = &root->rb_node;   // 指向"当前要看的槽位"
    struct rb_node  *parent = NULL;

    while (*new) {                            // 1. 自己走树找位置
        struct my_type *this = container_of(*new, struct my_type, node);
        parent = *new;
        if (data->key < this->key)
            new = &((*new)->rb_left);
        else if (data->key > this->key)
            new = &((*new)->rb_right);
        else
            return;                       // 重复键,不插
    }

    rb_link_node(&data->node, parent, new);   // 2. 挂上树形
    rb_insert_color(&data->node, root);       // 3. 重新平衡
}

看到 **new 了么?跟第 2 课 hlist 的 **pprev 是同一个套路: 一个指向"指针的指针",用来在找到位置后直接把新节点写进正确的槽位。你已经懂这个手法了。

真实用例:调度器(以及一个必须纠正的旧说法)

用例 A:进程调度器 —— rbtree 仍在用,但要说对名字

很多老资料说"CFS 用红黑树,按 vruntime 排序"。这话在 6.6 已经不准确了:

版本调度算法rbtree 按…排序
2.6.23 ~ 6.5CFS(完全公平调度)vruntime(虚拟运行时间,最小者在最左)
6.6 起EEVDF(CFS 的继任者)虚拟截止时间(virtual deadline)

rbtree 本身没被换掉——cfs_rq 里的 tasks_timeline(一棵 rb_root_cached)、 sched_entity 里嵌入的 rb_node 都还在。换的是排序的键:从 vruntime 改成虚拟截止时间。 EEVDF 的核心思想是"给每个就绪任务算一个截止时间,谁截止最早谁先跑",rbtree 用来高效取"截止最早者"(最左节点)。

记忆纠偏 在你的环境(6.6.87.2)里,说"调度器用 rbtree"对,但说"CFS 用 rbtree 按 vruntime 排"就过时了。 内核在演进,术语要跟着版本走——这正是读 LWN 跟踪社区变化的理由。本书对应 6.2,接近 EEVDF 切换点,读到调度篇时(§14)要注意这个时间线。

用例 B:进程地址空间 VMA —— rbtree 已被取代

这是另一个必须当场纠正的常见说法。老资料常说"进程的 VMA(虚拟内存区域)用红黑树组织"。这在 6.1 已经变了:

版本VMA 存储结构
≤ 6.0mm_struct 里一棵 rbtree + 一个链表(双索引)
6.1 起maple tree(mm_struct.mm_mt)取代了 rbtree + 链表

maple tree 是一种 RCU 安全、基于 B 树、对缓存友好的区间树,专为"非重叠的地址区间"设计。 它在 VMA 这个场景(频繁按地址区间查找)上比 rbtree 更快、更好用。你的 6.6 内核里,VMA 已经不在 rbtree 里了。

这堂课的元教训 红黑树仍是内核主力数据结构(CFS/EEVDF 调度、ext4 区段树、timerfd、keyctl、内存 cgroup…), 但具体用在哪随版本变化。读到"X 用 rbtree"时,在心里加一句"截至某版本",并准备查证。 这就是为什么主教材标了"基于 6.x"——版本敏感是内核学习的常态。

动手实验:维护一棵真实的 rbtree

目标:写一个 .ko,用真实 struct rb_node 维护一棵按"设备 id"排序的红黑树。 插入 5 个节点(故意乱序),加载时中序遍历打印(应看到升序输出),卸载时清空。 你会亲手写出"自己找位置 + rb_link_node + rb_insert_color"这套内核标准插入模式。

源码 bt_rbtree.c

// bt_rbtree.c — 第 3 课实验:真实内核红黑树
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/rbtree.h>
#include <linux/slab.h>

struct bt_dev {
    int               id;            // 排序键
    char              name[16];
    struct rb_node    node;          // ← 嵌入红黑树节点
};

static struct rb_root bt_tree = RB_ROOT;

/* 自己写插入:遍历找位置 → rb_link_node → rb_insert_color */
static int bt_insert(struct rb_root *root, struct bt_dev *dev)
{
    struct rb_node **new  = &root->rb_node;
    struct rb_node  *parent = NULL;

    while (*new) {
        struct bt_dev *cur = container_of(*new, struct bt_dev, node);
        parent = *new;
        if (dev->id < cur->id)
            new = &(*new)->rb_left;
        else if (dev->id > cur->id)
            new = &(*new)->rb_right;
        else
            return -EEXIST;       // 重复 id 不插
    }
    rb_link_node(&dev->node, parent, new);
    rb_insert_color(&dev->node, root);
    return 0;
}

static int __init bt_rb_init(void)
{
    int i;
    int ids[] = { 30, 10, 50, 20, 40 };   // 故意乱序
    struct bt_dev *dev;

    pr_info("bt_rb: 加载,按乱序插入 {30,10,50,20,40}\n");
    for (i = 0; i < 5; i++) {
        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (!dev) return -ENOMEM;
        dev->id = ids[i];
        scnprintf(dev->name, sizeof(dev->name), "BT-%d", ids[i]);
        bt_insert(&bt_tree, dev);
    }

    // 中序遍历:rb_first + rb_next,应得到升序
    pr_info("bt_rb: 中序遍历(应为升序):\n");
    struct rb_node *n;
    for (n = rb_first(&bt_tree); n; n = rb_next(n)) {
        struct bt_dev *d = container_of(n, struct bt_dev, node);
        pr_info("  - id=%d %s\n", d->id, d->name);
    }
    return 0;
}

static void __exit bt_rb_exit(void)
{
    struct rb_node *n, *tmp;
    for (n = rb_first(&bt_tree); n; n = tmp) {
        tmp = rb_next(n);                   // 先记下后继,再删当前
        struct bt_dev *d = container_of(n, struct bt_dev, node);
        rb_erase(n, &bt_tree);
        kfree(d);
    }
    pr_info("bt_rb: 卸载\n");
}

module_init(bt_rb_init);
module_exit(bt_rb_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 3: real kernel rbtree demo");

跑起来(Makefile 同前两课,把 obj-m 改成 bt_rbtree.o)

  1. make → bt_rbtree.ko
  2. sudo insmod bt_rbtree.ko
  3. dmesg | tail —— 中序遍历应输出 id=10, 20, 30, 40, 50(升序),即使插入顺序是乱的
  4. sudo rmmod bt_rbtree
观察重点 你插入的顺序是 {30,10,50,20,40},遍历输出却是 {10,20,30,40,50}——这就是"二叉搜索树中序有序"。 而 rbtree 保证这棵树在乱序插入后依然近似平衡,所以每次插入都是 O(log n) 而非退化成 O(n) 链。 你可以在加载后查 /proc/kallsyms 里 rb_insert_color 确认它确实被调用了。

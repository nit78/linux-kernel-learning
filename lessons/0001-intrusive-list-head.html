list_head：侵入式链表——内核数据结构的基石

你做过蓝牙/WiFi 驱动移植，一定见过代码里满屏的 list_for_each_entry 和 container_of。 移植时"照搬能用"，但要说清为什么内核这样组织链表，就是从"移植"到"内核工程师"的第一道坎。 这节课打通这道坎。

为什么从这一课开始 list_head 是后续几乎每一章的地基：进程链表、页的 LRU、VFS 的 inode 链、 设备模型里的 device/driver/bus 全靠它串起来。 把它吃透，后面读内核源码的门槛会下降一大截。

思维转换：两种链表

你熟悉的链表（裸机/MCU 教科书里）长这样：

// MCU 教科书式：节点"持有"数据
struct node {
    int        value;     // ← 数据在这里面
    struct node *next;
};

而内核的链表节点不含任何数据，只有一个"挂钩"：

// include/linux/types.h
struct list_head {
    struct list_head *next, *prev;
};

数据结构反过来"嵌入"这个挂钩。这就是侵入式链表（intrusive list）。

MCU / 教科书链表

链表节点持有数据；next 指向下一个含数据的节点。

  • 链表代码绑死某一种数据类型
  • 每个数据类型要单独写一遍增删改查
  • 一个对象只能在一条链上

Linux 内核链表

链表节点不含数据；数据结构里嵌入 list_head 成员，next/prev 指向相邻节点的那个成员。

  • 链表代码与数据类型完全解耦
  • 一套 list_* API 服务所有数据类型
  • 同一对象嵌入多个 list_head 就能同时挂在多条链上

对比内存布局，差别一目了然。假设有 3 个蓝牙设备：

内核侵入式链表：节点不带数据，数据带节点 bt_device[0] bt_device[1] bt_device[2] ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ name = "BT-A" │ │ name = "BT-B" │ │ name = "BT-C" │ │ addr = 0x1122 │ │ addr = 0x3344 │ │ addr = 0x5566 │ │ list ────────────────────→ list ────────────────────→ list ─┐ │ ↑ ───────────────────────────────────────────────── │ │ └──────│───────────┘ └─────────────────┘ └─────────────────┘ │ └───────────────────────────────────────────────────────────────────←──────┘ （循环：最后一个 next 指回头节点） 链表本身只有一个"头"，带头双向循环。

关键魔法：container_of

侵入式链表带来一个必然问题：遍历时我手上只有 list_head * 指针， 怎么拿到"拥有它的那个 bt_device"？答案就是 container_of： 

// include/linux/container_of.h （简化版）
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

原理只有三步，画出来就懂了：

bt_device 结构体在内存中的样子（成员 list 在偏移 64 字节处）： 基址 0x1000 0x1040 ↓ ↓ (ptr 指向这里) ┌──────────┬──────────┬─────────┬─────────┬─────────────┐ │ name[32] │ addr │ power │ state │ list (list_head) │ └──────────┴──────────┴─────────┴─────────┴─────────────┘ ←────────────── offsetof(bt_device, list) = 64 ──────────→ container_of(ptr, bt_device, list) = (char*)ptr - 64 = 0x1000 ← 宿主基址
为什么用 (char *) 强转 offsetof 返回的是字节数。把 ptr 先转成 char *（按字节运算的指针）， 减去字节数后，地址算术才正确；再转成宿主类型 type *。这是 C 指针算术的标准技巧。

五个最常用的 API

掌握这五个，你就能读懂内核里 80% 的链表代码：

API做什么
INIT_LIST_HEAD(&head)初始化一个头节点，next/prev 都指向自己（空循环链表）。
list_add(&new, &head)把 new 插到 head 之后（头插法）。
list_del(&entry)从链表中摘除 entry（注意摘除后要把它的指针置为无效，见 LIST_POISON）。
list_for_each(pos, &head)遍历，pos 是 list_head *，你拿到的是节点，不是数据。
list_for_each_entry(item, &head, member)遍历并自动用 container_of 取出宿主，item 直接就是 bt_device *。最常用。

动手实验：一个能跑的 .ko

你的目标是写一个内核模块：定义含 list_head 的"蓝牙设备"结构体， 在加载时链起 3 个节点并打印，卸载时清空。加载后用 dmesg 看结果—— 这就是你移植驱动时每次都见、但从没亲手写过那套链表操作。

前提 你需要内核头文件和构建能力。在 Ubuntu/Debian 上：sudo apt install build-essential linux-headers-$(uname -r)。 QEMU 里同样适用。

① 模块源码 bt_list.c

// bt_list.c — 第 1 课实验：用 list_head 管理蓝牙设备
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/list.h>
#include <linux/slab.h>

struct bt_device {
    char              name[16];
    u16               addr;        // 模拟蓝牙地址
    struct list_head  list;        // ← 嵌入的挂钩
};

static LIST_HEAD(bt_devices);          // 声明并初始化链表头

static int __init bt_list_init(void)
{
    int i;
    struct bt_device *dev;

    pr_info("bt_list: 加载\n");

    // 创建并链入 3 个设备
    for (i = 0; i < 3; i++) {
        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (!dev)
            return -ENOMEM;

        scnprintf(dev->name, sizeof(dev->name), "BT-%c", 'A' + i);
        dev->addr = 0x1000 * (i + 1);

        // 关键：把 dev->list 挂到 bt_devices 上
        INIT_LIST_HEAD(&dev->list);
        list_add(&dev->list, &bt_devices);
    }

    // 遍历：list_for_each_entry 自动用 container_of 取出宿主
    pr_info("bt_list: 当前设备链表:\n");
    list_for_each_entry(dev, &bt_devices, list) {
        pr_info("  - %s (addr=0x%04x)\n", dev->name, dev->addr);
    }
    return 0;
}

static void __exit bt_list_exit(void)
{
    struct bt_device *dev, *tmp;

    // 安全遍历+删除：边遍历边 free 必须用 _safe 版本
    list_for_each_entry_safe(dev, tmp, &bt_devices, list) {
        pr_info("bt_list: 摘除 %s\n", dev->name);
        list_del(&dev->list);
        kfree(dev);
    }
    pr_info("bt_list: 卸载\n");
}

module_init(bt_list_init);
module_exit(bt_list_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("kernel-student");
MODULE_DESCRIPTION("Lesson 1: intrusive list_head demo");

② Makefile（与源码同目录）

obj-m += bt_list.o

KDIR ?= /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

③ 跑起来

  1. 编译：make → 生成 bt_list.ko
  2. 加载：sudo insmod bt_list.ko
  3. 看日志：dmesg | tail —— 应看到 3 个设备被链入并打印
  4. 卸载：sudo rmmod bt_list
  5. 再看日志：dmesg | tail —— 应看到逐个摘除
预期输出 加载时逆序打印（因为用了头插法 list_add）：BT-C → BT-B → BT-A。 如果顺序反了，正是你理解 list_add 行为的第一手证据——动手看到它，比读十遍文档都牢。

内核同步基础:SMP 时代的竞争与锁

这是附录 B 内核同步的上半篇。附录 B 不是书的"正文章节",却是三大核心篇的必备前置—— 内存管理、进程调度、文件系统每一处都要用锁。这课讲清"为什么需要锁、有哪些锁、何时用哪个"; 下一课(第 8 课)单独深讲 RCU(§B.2.12),它是内核最精巧、最值得专门一课的同步机制。

连接点 同步的根基是第 4 课的上下文铁律:"能不能睡眠看上下文"。这课整张选型表,本质上都在回答 "我当前在什么上下文 → 我能用哪种锁"。你的 MCU 单核经验里锁很简单,内核的复杂全来自 SMP + 中断 + 抢占的组合。

§B.1 为什么内核需要同步

一句话:多个执行流(CPU 核、中断、线程)同时访问同一份共享数据,结果会错。

你在 MCU 单核上很少操心这个——一次只有一个执行流。但内核跑在 SMP(多核)上,竞争来自三个维度叠加:

竞争来源含义
多 CPU 核核 0 和核 1 真的同时读写同一变量
中断进程正在改数据时,中断打断进来也改它
抢占进程 A 改数据到一半被调度走,进程 B 接着改

看一个最典型的竞争——`count++` 不是原子的:

count++ 的竞争(读-改-写三步,中间能被打断) count = 0 CPU 核 0: 读 count (得 0) CPU 核 1: 读 count (也得 0!) CPU 核 0: 加 1 (得 1) CPU 核 1: 加 1 (也得 1) CPU 核 0: 写回 count (=1) CPU 核 1: 写回 count (=1) 结果:两次 ++ 只涨了 1。这就是竞争(race condition)。 解法:把"读-改-写"包成不可分割的原子操作,或加锁。

先看免锁的招数(§B.2.1–§B.2.4)

加锁有开销,内核先尽量"不加锁"。四种常用免锁手段:

§B.2.1 每 CPU 变量(percpu)——各核各一份

// 给每个 CPU 核一份独立副本,写自己的不会竞争
static DEFINE_PER_CPU(unsigned long, bt_counter);

// 当前核上加:无需锁!
this_cpu_inc(bt_counter);

// 要总数时再加起来(此时才需考虑同步)
unsigned long total = 0;
int cpu;
for_each_possible_cpu(cpu)
    total += per_cpu(bt_counter, cpu);

适合高频计数器/统计。只要每个核只动自己的副本,就零竞争。

§B.2.2 volatile——内核不推荐你写它

本书会介绍 volatile,但内核明确不推荐用裸 volatile 做并发通信 (编译器语义不够、易错)。现代替代是下面的 READ_ONCE/WRITE_ONCE。读老代码会遇到 volatile,要能看懂,但别新写。

§B.2.3 内存屏障(memory barrier)

编译器和 CPU 都会乱序读写(为了性能)。需要严格顺序时插屏障: smp_mb()(全屏障)、smp_rmb()(读屏障)、smp_wmb()(写屏障)。 进阶话题,这课不展开,第 8 课讲 RCU 时会涉及。日常用 READ_ONCE/WRITE_ONCE 即可。

§B.2.4 原子变量(atomic_t)——单变量的原子读-改-写

#include <linux/atomic.h>
atomic_t bt_count = ATOMIC_INIT(0);

atomic_inc(&bt_count);              // 原子 +1
atomic_add(5, &bt_count);          // 原子 +5
int v = atomic_read(&bt_count);    // 原子读
if (atomic_inc_return(&bt_count) == 1) { ... }   // 原子 +1 并返回新值

单变量的 ++/--/add/read 都有原子版,无需锁。比 percpu 重,但跨核。

READ_ONCE / WRITE_ONCE(现代推荐)

对单个变量的并发访问(只需"读/写本身不被编译器拆碎",不要求读-改-写原子),内核推荐用 READ_ONCE(x) / WRITE_ONCE(x, v)——它们防编译器撕裂/融合/消除读写, 相当于 C11 的 memory_order_relaxed。比裸读、裸写、volatile 都更明确。 读写场景常这样配:WRITE_ONCE(flag, 1) 在一边,while(!READ_ONCE(flag)) 在另一边。

两把主力锁:spinlock 与 mutex

多变量、复合操作,免锁手段不够,就用锁。内核两把主力:

spinlock(自旋锁)

抢不到就忙等(CPU 空转循环重试)。绝不睡眠。

适用:短临界区;中断上下文也能用(因为它不睡)。

代价:持锁期间本核会忙等;持锁时绝不能睡眠(否则死锁——其他核会死等)。

mutex(互斥锁)

抢不到就睡眠让出 CPU,被唤醒后再来。

适用:长临界区;仅进程上下文(因为它会睡)。

代价:睡眠/唤醒有调度开销;中断上下文绝不能用。

选型核心又是第 4 课的上下文铁律:临界区里要睡眠(分配大内存、做 I/O)→ mutex; 临界区不能睡(在中断、软中断里)→ spinlock。

§B.2.7 自旋锁的四个变体(关键)

spinlock 最让人晕的是它有四个变体,差别在持锁时还要不要关中断/软中断:

变体关中断?关软中断?保存状态?何时用
spin_lock()否否—锁绝不会在中断上下文被获取
spin_lock_bh()否✅—数据与软中断/tasklet共享(§B.2.5)
spin_lock_irq()✅✅否确定进入前中断是开的
spin_lock_irqsave()✅✅✅最通用安全:锁可能在中断上下文被获取

为什么有 irqsave? 想象你的锁可能在中断里被获取:进程持锁 → 中断来 → 中断也想要这把锁 → 死锁(进程被中断打断、又没法释放锁)。解法是进程持锁时先关本核中断。 irqsave 额外保存了之前的中断状态,以便 unlock 时恢复原状(可能进来时中断本来就是关的)。

实战建议

不确定时,优先 spin_lock_irqsave(&lock, flags) / spin_unlock_irqrestore(&lock, flags)—— 它最安全,覆盖了所有情况。性能敏感的热路径才精挑细选更轻的变体。

§B.2.10 信号量 / §B.2.11 mutex 的 API

// mutex(进程上下文、可睡眠)
DEFINE_MUTEX(bt_mutex);
mutex_lock(&bt_mutex);       // 获取,获取不到就睡眠
/* 临界区:可睡眠、可做 I/O */
mutex_unlock(&bt_mutex);

// 信号量:可用作"计数信号量"(允许 N 个同时进)或互斥(=mutex 的底层)
struct semaphore sem;
sema_init(&sem, 1);         // 初值 1 = 互斥
down(&sem);                 // 获取(可睡)
up(&sem);                   // 释放 */

§B.2.8–§B.2.9 其他锁:rwlock 与 seqlock

当读多写少,普通锁会让所有读者互相阻塞,有更优结构:

结构读者写者典型场景
rwlock(读写锁 §B.2.8)共享(多读并发)独占读多写少,但写仍需等所有读
seqlock(顺序锁 §B.2.9)无锁(读时记序号)独占(写时序号++)极少写、读者不要阻塞写(如时间戳、统计)

seqlock 的精巧:读者不加锁,只在读前后各读一次序号;若两次序号不同(说明中间有写)或序号为奇数(写进行中),就重读。写者完全不被读者阻塞。

// seqlock 典型用法(读 x,写者可能正在改)
unsigned int seq;
u64 val;
do {
    seq = read_seqbegin(&bt_seq);
    val = READ_ONCE(bt_val);     // 顺手用 READ_ONCE
} while (read_seqretry(&bt_seq, seq));   // 中途被写打扰就重来

// 写者:
write_seqlock(&bt_seq);
bt_val = new_value;
write_sequnlock(&bt_seq);

场景用理由

心智模型:先问"共享数据长什么样"——单变量?多变量?读多还是写多?再问"我在什么上下文"——能不能睡?——选型就出来了。

动手实验:percpu vs spinlock 的开销(WSL2 可跑)

目标:同一个计数器,分别用 percpu 和 spinlock 实现,各加 1000 万次,对比耗时。 你会亲手量到锁的开销——这是"为什么内核要发明这么多免锁招数"的第一手证据。 

// bt_sync.c — 第 7 课实验:percpu vs spinlock 计数器开销
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/percpu.h>
#include <linux/spinlock.h>
#include <linux/ktime.h>

static DEFINE_PER_CPU(unsigned long, bt_pcpu);
static unsigned long __percpu *bt_pcpu_ptr;
static DEFINE_SPINLOCK(bt_lock);
static unsigned long bt_shared;
#define N 10000000UL

static void bench_percpu(void)
{
    int i; ktime_t t = ktime_get();
    for (i = 0; i < N; i++)
        this_cpu_inc(*bt_pcpu_ptr);
    pr_info("bt_sync: percpu   %lu 次耗时 %lld ns\n", N, ktime_to_ns(ktime_sub(ktime_get(), t)));
}

static void bench_spinlock(void)
{
    int i; unsigned long flags; ktime_t t = ktime_get();
    for (i = 0; i < N; i++) {
        spin_lock_irqsave(&bt_lock, flags);
        bt_shared++;
        spin_unlock_irqrestore(&bt_lock, flags);
    }
    pr_info("bt_sync: spinlock %lu 次耗时 %lld ns\n", N, ktime_to_ns(ktime_sub(ktime_get(), t)));
}

static int __init bt_sync_init(void)
{
    bt_pcpu_ptr = alloc_percpu(unsigned long);
    if (!bt_pcpu_ptr) return -ENOMEM;
    pr_info("bt_sync: 加载,开始 %lu 次累加对比\n", N);
    bench_percpu();
    bench_spinlock();
    pr_info("bt_sync: shared=%lu percpu 总和=%lu\n", bt_shared,
            bt_pcpu_ptr[0] + bt_pcpu_ptr[1] + (nr_cpu_ids > 2 ? bt_pcpu_ptr[2] : 0));
    return 0;
}

static void __exit bt_sync_exit(void)
{
    free_percpu(bt_pcpu_ptr);
    pr_info("bt_sync: 卸载\n");
}
module_init(bt_sync_init);
module_exit(bt_sync_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Lesson 7: percpu vs spinlock cost");
  1. make → bt_sync.ko
  2. sudo insmod bt_sync.ko
  3. dmesg | tail —— 应看到两行耗时,percpu 明显快于 spinlock(差几倍很正常)
  4. sudo rmmod bt_sync
观察重点

percpu 快,是因为它零竞争(只动自己核的副本);spinlock 慢,是因为每次 spin_lock_irqsave 都要关中断 + 原子操作 + (可能)等别的核。这就是内核发明 percpu / atomic / RCU 这些免锁/轻锁机制的回报—— 在热路径上,几倍的开销差距是真实可感的。这个数字你亲眼看到了,以后选型就有直觉。
